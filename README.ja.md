# Aequera

> Firefox/Geckoベースで、人間中心のUX、応答性、シンプルさ、深いカスタマイズ性、プライバシー、そして完全なデフォルト体験を設計したブラウザ。

AequeraはFirefox/Geckoをベースにしたブラウザプロジェクトです。このプロジェクトは、ブラウザシェル——インターフェイス、ワークフロー、ナビゲーションモデル、カスタマイズシステム、モーション、マテリアル、インタラクションアーキテクチャ——をウェブプラットフォームの薄いレイヤーではなく、ファーストクラスのプロダクトとして扱います。

Aequeraはいくつかのブラウザカテゴリの強みを組み合わせ、どれかのコピーになることを避けることを意図しています：

- **Firefox/Gecko** — 成熟したウェブプラットフォームおよび拡張機能の基盤として。
- **Arc/Zenをイメージしたアイデア** — ブラウザワークフロー、ワークスペース、ナビゲーション、ブラウザシェルUXの再考のインスピレーションとして。
- **Heliumをイメージした軽量性** — 抑制された、低オーバーヘッドのブラウザシェルと応答性への強い注力のインスピレーションとして。
- **LibreWolfをイメージしたプライバシー規律** — プライバシー優先のデフォルト、監査可能な設定、不要なテレメトリ/広告動作の削除のインスピレーションとして。

これらは参照点であり、実装テンプレートではありません。Aequeraはヒューマンファクターズ、測定可能なUX目標、一貫性のあるアーキテクチャから独自のインタラクションモデルを発展させるべきです。

## コアアイデア

Aequeraは、広範な能力表面をシンプルにすることを目指しています：

```text
大規模な能力表面
          ↓
一貫性のある情報アーキテクチャ
          ↓
少数のメンタルコンセプト
          ↓
高速なフィードバック + 予測可能な状態
          ↓
パーソナルブラウザ
```

プロジェクトは以下のバランスを明示的に求めています：

- シンプルさと能力;
- パフォーマンスと視覚的豊かさ;
- オートメーションとユーザー制御;
- 一貫性とパーソナライゼーション;
- 探索と集中;
- 強力なデフォルト体験と深いカスタマイゼーション。

## 「デフォルトで完備」とは

Aequeraは最初の起動から完成した状態であるべきです。新しいユーザーは、ブラウザが役立つようになる前に大規模な拡張機能スタックをインストールしたり複雑な設定システムを学んだりする必要はありません。

同時に、上級ユーザーはプライベートなソースフォークを維持することなく、プレゼンテーションとワークフローを大幅に再構築できるべきです。

「オールインワン」とは、統合されていることを意味し、「ありとあらゆる機能を含む」ことを意味しません。タブ、ワークスペース、検索、履歴、ブックマーク、ダウンロード、パーミッション、セッション、コマンド、設定、拡張機能は、共有のブラウザモデルの一部として動作すべきです。

## UX原則

Aequeraは機能中心ではなく人間中心です。

中心的なインタラクションループは：

```text
意図 → 即時フィードバック → 予測可能な状態 → 最小限の修正
```

ブラウザは以下を削減すべきです：

- 視覚的な検索時間;
- ポインターの移動と繰り返されるモーター労力;
- 不要なクリック;
- モードの混乱;
- 重複するナビゲーション概念;
- ブラウザシェルのフィードバックを待つこと;
- 繰り返される設定作業。

応答性はUXプロパティとみなされます。パフォーマンス作業は、ページベンチマークだけでなく、入力遅延、視覚的フィードバック、フレームの一貫性、起動、メモリ動作、アイドルCPU、重いウェブコンテンツワークロード下でのブラウザクロームのレジリエンスに基づいて評価されます。

## 視覚とインタラクションシステム

Aequeraは、意味的価値を持つ場合にのみリッチなUIを意図的に許容します。ブラー、半透明、グラデーション、深さ、エレベーション、タイポグラフィ、モーション、密度は、それ自体のための装飾ではなく、階層、状態、コンテキスト、連続性のためのツールです。

デザインシステムには以下が含まれます：

- セマンティックデザイントークン;
- タイポグラフィと密度;
- サーフェスとマテリアル;
- モーションロールとイージング;
- フォーカス/ホバー/アクティブ/無効状態;
- アクセシビリティとリデュースドモーション;
- エルゴノミックなターゲットと到達可能性ルール。

アニメーションはインタラクションシステムとして扱われます。トランジションは短く、中断可能で、可能な限りコンポジッターフレンドリーであり、新しいユーザー意図によって即座に上書きされるべきです。

## 深いカスタマイゼーション

カスタマイゼーションはレイヤー化されており、一般ユーザーはシンプルに留まり、上級ユーザーは精度を得ることができます：

```text
ネイティブ設定
      ↓
プロファイル / 値
      ↓
テーマ / CSS
      ↓
Firefox WebExtensions
      ↓
AequeraブラウザシェルAPI
```

設定モデルは型付けされ、ドキュメント化され、バージョン化された値を使用し、決定論的な優先順位、バリデーション、マイグレーション、リカバリを持つべきです。カスタマイゼーションは隠れたセキュリティ境界の脱出になってはなりません。

概念的に：

```toml
ui.sidebar.position = "left"
ui.sidebar.width = 280px
ui.tabs.presentation = "icon-title"
ui.tabs.density = "compact"
workspace.presentation = "expanded"
material.sidebar.type = "frosted"
motion.global.profile = "balanced"
```

正確な構文は実装上の決定ですが、予測可能なセマンティクスはそうではありません。

## Firefox互換性

Firefox WebExtensionsは主要な互換性のターゲットのままです。既存のFirefoxアドオンは、Aequeraのシェルアーキテクチャが許容する限り動作するべきであり、プロジェクト固有のAPIは不要に独自的なものではなく、追加的で能力スコープされたものであるべきです。

ファーストパーティの組み込みWebExtensionとして実装できる機能は、パフォーマンス、UXの整合性、セキュリティを損なわない限り、より深い特権ソース変更を導入する前に一般的に検討されるべきです。

## プライバシーとユーザー制御

プライバシーはプロダクト要件です。Aequeraは以下を導入すべきではありません：

- 明示的な同意なしのテレメトリ;
- 広告またはスポンサーされたUI;
- 通常のブラウジングのための強制アカウント;
- 不要なベンダーサービス;
- サイレントなリモート設定;
- 不要なバックグラウンド活動やデータ収集。

ネットワーク活動はユーザーに見えるかプラットフォームで必要とされる理由を持つ必要があり、セキュリティに敏感な動作は通常のカスタマイゼーションから保護されなければなりません。

## 上流アーキテクチャ

Aequeraは永続的に手動で編集されたFirefoxフォークになってはなりません。

優先されるソースオブトゥルースモデルは：

```text
Mozilla Firefox / Gecko
        ↓
 pinned upstream revision
        ↓
 clean upstream source
        ↓
 reproducible Aequera patchset
        ↓
 Aequera-owned source + configuration
        ↓
 build / test / benchmark
        ↓
 Aequera artifact
```

重要な境界は：

> **Aequera-owned code is source; Firefox modifications are an explicit, reviewable patchset.**

上流Firefoxは入力/アーティファクトとして扱われ、Aequeraのプロダクトアイデンティティが存在する場所ではありません。

## プロジェクトステータス

現在のステージ：**アーキテクチャと基盤**。

直近の作業は、再現可能なFirefoxベースラインの確立、ソース/パッチ/設定境界の形式化、測定可能なパフォーマンスインストゥルメンテーションの確立、そしてプロジェクトが巨大で未分化のフォークになることなく最初のブラウザシェル基盤を構築することです。

## 名前

**Aequera**はラテン語の*aequus*（バランスが取れた、調和のとれた、等しい）と*era*のアイデアにインスパイアされた造語です。

プロジェクトは、バランスのとれた、人間中心の、適応可能なコンピューティングとブラウジングの新時代を表現するためにこの名前を使用します。
